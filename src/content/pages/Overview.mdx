# Overview

Backyard Flyer is an interactive learning environment for quadcopter control fundamentals. The goal is to build intuition for how a real flight controller works — not by reading about it, but by running the code, breaking it, and watching what happens.

The course walks through increasingly realistic simulations, starting from a single incrementing counter and working up to a quad copter with attitude control. Each simulation runs live in the browser: you can read the source, edit any block of the flight controller or physics model, stage your changes, and restart to see the effect immediately.

Use the table of contents on the left to navigate. Simulation pages have three tabs — **Chapter** for the explanation, **Source** to edit the model blocks, and **Visualization** for the 3D scene, live charts, and playback scrubber. The **[Simulation Catalog](#sim-demo/catalog)** lists every model in one place so you can browse and run any of them without leaving a single page.

## [Backyard Flyer](#Backyard-Flyer)

Quadcopter simulations in order of increasing realism — from a point-mass sphere to a full cascaded flight controller flying through window gates.

⭐ **New here? Start with [Quad L4](#Backyard-Flyer/quad-l4).** L1–L3 trace how the flight controller is built up; **L4 is where that flight is reorganized into the architecture every subsequent model is built on** — a shared block library, static constants delivered through `state.K`, and a lifecycle block that owns setup, validation, and pass/fail testing. Later models add disturbances and gates *on top of* this skeleton rather than reinventing it.

| Model | Description | New since previous |
|---|---|---|
| [**Floater**](#Backyard-Flyer/floater) | Sphere chasing 3D waypoints through a simulated hardware actuator | **4-block layered architecture** (`mission → fc → hw → world`), nested state sub-trees, actuator thrust inertia |
| [**Floater PID vs PD**](#Backyard-Flyer/floater-pid) | Two floaters on mirrored paths — one PD controller, one PID | **A/B control law comparison**; visible effect of the integral term on steady-state drift |
| [**Quad L1**](#Backyard-Flyer/quad-l1) | Quadrotor executing a full autonomous waypoint mission | **Quadrotor physics** (4-motor layout, differential torque, ground contact), **7-phase mission state machine** (arm → takeoff → navigate → RTH → land → disarm) |
| [**Quad L2**](#Backyard-Flyer/quad-l2) | Same mission with a split flight controller | **Cascaded FC**: `fc_navigator` (position → desired attitude) + `fc_stabilizer` (attitude → motors); live interface chart |
| [**Quad L3**](#Backyard-Flyer/quad-l3) | L2 with yaw-aware navigation | **Body-frame rotation** of position demands; yaw setpoint chases each waypoint heading |
| [**Quad L4** ⭐](#Backyard-Flyer/quad-l4) | A simplified waypoint quad, restructured into the **canonical architecture every later model inherits** — shared block library, static constants, and lifecycle hooks. If you read one model in depth, read this one. | **Shared block library** (blocks live in a reusable `lib/quad`, imported per model); **static `state.K` constants** (frozen consts bag + route, kept out of per-tick history); **lifecycle block** (`beforeSim`/`before`/`after`/`afterSim`) owning setup, the cross-track validator, and a **multi-criteria pass/fail test** (5 laps · within tick budget · lap & avg error limits); **mission as pure phase/step sequencer**; `planner_wp` as a **completion checker only**; `navigator_wp` flying straight at the active waypoint with **horizontal-only heading**; **rate-only `fc_acro`**; **AETR** stick bus |
| [**Quad Noise** ⭐](#Backyard-Flyer/quad-noise) | Quad L4 with real-world disturbances | **Same shared L4 block architecture** (`lifecycle`, `mission`, `planner_wp`, `navigator_wp`, `fc_acro`, `hw`, `world`) plus shared `wind` and `noise` disturbance blocks, **wind gusts** and **sensor noise**, a looser disturbance-specific pass threshold (`ACC_ERR_LIMIT = 1500`), and the same overlay-based pass/fail scoring |
| [**Quad W1a**](#Backyard-Flyer/quad-w1a) | Four rectangular window gates the drone must fly through | **Window gate** plane-crossing detection in shared `planner_w1a`, **pure-pursuit carrot on the gate centerline** (forward pull never collapses at the frame), yaw aligned to gate normal with a measurement low-pass, mission-owned **`PHASE_RESTART`** recovery + **restart-budget pass criterion** |
| [**Quad W1b**](#Backyard-Flyer/quad-w1b) | W1a with a smarter gate approach | **Pre-stage waypoint** on the approach axis (shared `planner_w1b`), `preGateDone` latch to prevent staging–gate oscillation; degrades to W1a when `preStageDist = 0` |
| [**Quad W1 Combined**](#Backyard-Flyer/quad-w1-combined) | W1a (Blue) vs W1b (Orange) flying under shared wind | **Dual-vehicle A/B comparison** (one shared stack wired twice under `state.vehicles.a/.b` on offset tracks), **per-vehicle PASS/FAIL**; laps-completed and restart-count charts show the planner difference over many laps |
| [**Quad C1a**](#Backyard-Flyer/quad-c1a) | Moving-target chase — drone intercepts a ghost target sliding around the rectangle before it completes a full circuit | **Chase family** (c1): `target_c1` kinematic ghost running its own continuous loop independent of mission step index; `planner_c1a` direct pursuit (carrot = target pos); `STATUS_RESTART` on target escape |
| [**Quad C1b**](#Backyard-Flyer/quad-c1b) | C1a with a pre-staged intercept approach | **Pre-stage for chase** (`planner_c1b`): fixed pre-stage point `preStageDist` along the target's trajectory, `preGateDone` latch, then direct pursuit; cyan indicator dot follows the active carrot; degrades to C1a when `preStageDist = 0` |
| [**Quad C2a**](#Backyard-Flyer/quad-c2a) | Chase where the target is a fully simulated quadrotor (first-class vehicle) | **c2 family**: target runs real flight controller + physics under `state.vehicles.target`; target uses `navigator_wp` (rate-feedback, same as L4/Noise); `planner_c2a` starts pursuit immediately from home pad (no staging detour); **velocity-lead pursuit** — carrot placed `K.LEAD_DIST` m ahead of target's current heading; successful intercept pulses `forceRTH` on target (both reset together); `STATUS_FAILED` when target enters RTH (phase ≥ 3); interceptor uses dedicated `navigator_c2` (c2 extension point); INTERCEPTED / INTERCEPTION FAILED flash banners; Wind/Noise/Trail OFF by default |

## [Racing](#Racing)

A separate collection of models for FPV racing maneuvers — gate geometries, path-planning tricks, and frame-aware control needed to fly racetrack elements rather than simple waypoint missions.

| Model | Description | New since previous |
|---|---|---|
| [**Quad Ladder** ⚠️](#Racing/quad-ladder) | Three-gate vertical FPV ladder with alternating gate normals | **Body-frame roll/pitch decomposition** for arbitrary yaw ψ; vertical mission geometry with switchback path between gates |
| [**Quad Pole** ⚠️](#Racing/quad-pole) | Acro-mode coordinated horizontal turn around a flagpole | **Acro flight controller** (pure rate inner loop, no attitude memory); **per-step planner/navigator dispatch** by mission type; **3-point arc fit** with bank angle φ = atan(v²/(g·r)) for a true coordinated turn |
| [**Quad Rates**](#Racing/quad-rates) | Scripted AETR stick commands over time — hover, fly, brake, spin 180°, return, land | **Time-based step completion** (`planner_rates`); **AETR interpolation** (`navigator_rates`); dual-navigator pipeline — position control for TAKEOFF/RTH/LAND, open-loop rates for NAVIGATE |

## [Control blocks](#control)

Standalone simulations focused on PID fundamentals: what each term does, how to tune a controller by hand, and two automatic tuning algorithms.

- **[PID tutorial — control fundamentals](#control/pid-tutorial)** — a single 1D plant driven by a PID controller. Live sliders for target, gains (Kp, Ki, Kd), and plant parameters (mass, damping) let you build intuition for what each term does — start with pure P, add D to damp oscillation, add I to kill steady-state error.

- **[PID auto-tuning — STR](#control/pid-tune-str)** ⚠️ *Work in progress.* Self-Tuning Regulator: identify the plant online with RLS, then derive PID gains via pole placement. Demonstrates the *idea* of model-based auto-tuning; the implementation can still drift or get stuck under aggressive setpoint changes.

- **[PID auto-tuning — Relay-feedback](#control/pid-tune-relay)** — Åström–Hägglund's relay method. Press *Tune Now* and the system temporarily replaces the PID with a bang-bang relay; the resulting limit cycle gives `Ku` and `Tu`, and Ziegler-Nichols yields the gains. This is the algorithm behind the "auto-tune" button on most industrial PID controllers.
