# Floater — multi-block model with simulated hardware

**Floater** is a sphere that flies through a sequence of waypoints in 3D space.
It demonstrates a four-block model where each block has a single responsibility and communicates only through shared state.

The simulation runs at **50 ms per tick** (20 Hz). Four blocks execute in order each tick:

```
mission → fc → hw → world
```

- **`mission`** — picks the next waypoint when the floater is close enough
- **`fc`** — flight controller; computes the desired thrust vector
- **`hw`** — hardware/actuator; applies real-engine inertia and limits
- **`world`** — physics; integrates the resulting force into motion

The `hw` block sits between the controller and the physics. It simulates real engine inertia and limits, so the controller's command no longer goes straight into motion: it has to fight a slow-spooling, slow-gimbaling actuator.

The state is structured into sub-trees (`pos`, `vel`, `thrust.desired`, `thrust.actual`, `mission.target`, …) so related variables stay together — easier to extend than a flat namespace.

## How it works — four blocks

### `mission.ts` — waypoint sequencer

Measures distance to the current target waypoint. When the floater is within `THRESHOLD` (1.5 m), it advances to the next waypoint and writes the new target into state.

**Outputs:** `mission.targetIdx`, `mission.dist`, `mission.target.{x,y,z}`

### `fc.ts` — flight controller

Reads `pos`, `vel`, and `mission.target` and computes the *desired thrust* as a world-frame vector. The vector's length is the throttle setting (`0–100 %`); its direction is where the engine should push.

Uses a proportional gain `K` and velocity damping `KV`. Gravity is compensated as a force (`MASS · GRAVITY`) so the floater can hover.

This is a deliberately simple P-only controller — the next model introduces PID and compares the two.

**Outputs:** `thrust.desired.{x,y,z}` (% throttle, world frame)

### `hw.ts` — hardware

The actuator model. Translates desired throttle (%) into actual thrust force (Newtons) while simulating real-engine limits:

- **Saturation** — magnitude clamped to `MAX_THRUST_N`
- **Spool inertia** — magnitude can only change at `THRUST_RATE_N_PER_S`
- **Gimbal slew** — direction can only rotate at `DIR_RATE_RAD_PER_S` (slerp)

The block lags behind the FC's command. This lag is the main reason a perfect controller still overshoots — and the reason real autopilots need integral and derivative terms.

**Outputs:** `thrust.actual.{x,y,z}` (Newtons, world frame)

### `world.ts` — physics

Receives the actual thrust force, adds gravity as a separate force, and integrates `F = m·a` with semi-implicit Euler. Bounces off the ground at `y = 0`.

`world` doesn't know anything about controllers or hardware — it only knows mass, gravity, and the force currently acting on the floater.

**Outputs:** `pos.{x,y,z}`, `vel.{x,y,z}`, `acc.{x,y,z}`

## Waypoints

The waypoints live only in `mission.ts`. The flight controller reads the resolved coordinates from state — there is no second copy.

| # | x | y | z |
|---|---|---|---|
| 0 | 0 | 5 | 0 |
| 1 | 10 | 5 | 0 |
| 2 | 10 | 10 | 10 |
| 3 | 0 | 5 | 15 |

The floater starts at the origin (ground level) and first climbs to waypoint 0, then cycles through the route.

## Things to experiment with

- **`K` in `fc.ts`** — proportional gain. Higher = faster pull toward target, but more overshoot.
- **`KV` in `fc.ts`** — velocity damping. Lower = oscillation appears; higher = sluggish but stable.
- **`DIR_RATE_RAD_PER_S` in `hw.ts`** — gimbal slew rate. Drop it to ~1.0 and the engine can't turn fast enough — the floater orbits past each waypoint before recovering.
- **`THRUST_RATE_N_PER_S` in `hw.ts`** — spool rate. Lower it for a sluggish engine that lags FC commands; you'll see the actual thrust trail the desired thrust.
- **`MAX_THRUST_N` in `hw.ts`** and `world.ts` — saturation. Reduce it and the engine can't keep up with aggressive controller commands.
- **`THRESHOLD` in `mission.ts`** — advance waypoints sooner (loose, ~3) or later (tight, ~0.5).
- Add a fifth waypoint to the `WAYPOINTS` array in `mission.ts`.
- Remove the ground bounce in `world.ts` and observe what happens on `y`.
