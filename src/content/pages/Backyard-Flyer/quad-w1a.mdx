# Quad W1a — window gates and carrot-and-stick navigation

**Quad W1a** replaces point waypoints with rectangular **window gates**. Instead of flying to a coordinate and stopping, the drone must physically pass *through* each 5 × 5 m frame to advance the mission — hovering nearby is not enough.

It keeps the same canonical architecture as [Quad L4](/Backyard-Flyer/quad-l4) and [Quad Noise](/Backyard-Flyer/quad-noise): the whole flight stack is shared `lib/quad` blocks, the `lifecycle` block owns the constants slice `state.K` and pass/fail scoring, and the model file is mostly wiring. Only two blocks are window-specific, and both are still shared library blocks:

```
lifecycle (beforeSim → state.K)
    │
    ▼
wind ──► world ──► noise ──► mission ──► planner_w1a ──► navigator_w1 ──► fc_acro ──► hw ──► world
                               ▲    ▲         │ ▲
                               │    └ planner_wp (recovery arrival)
                               └──────── noisy sensors ───────┘
```

| Block | Role |
|-------|------|
| `mission` | Shared generic sequencer. The window route (`state.K.steps`) is a list of gates; mission only reads each step's `pos` and delegates completion to the planner |
| `planner_w1a` | **New.** Owns window logic: a pure-pursuit carrot on the gate centerline **and** through-the-frame crossing detection |
| `planner_wp` | Shared waypoint checker, reused to report arrival back at the recovery anchor during a restart |
| `navigator_w1` | Shared w1-family navigator: turns the planner's carrot + yaw setpoint into AETR sticks |
| `lifecycle`, `fc_acro`, `hw`, `world`, `wind`, `noise` | Shared, unchanged |

## Window gates

A gate is a rectangular plane in 3D space. In the shared `StepDef`, `pos` is the gate center and the window-specific fields ride the mission bus untouched:

```typescript
type StepDef = {
  pos: Vec3;       // gate center
  normal?: Vec3;   // unit vector — intended travel direction through the gate
  width?: number;
  height?: number;
};
```

The four gates form a 20 × 20 m rectangle at cruise altitude; the drone flies *through* each frame:

| Gate | Center | Normal (travel direction) |
|------|--------|--------------------------|
| 0 | (10, 5, −10) | +X |
| 1 | (10, 5, +10) | +Z |
| 2 | (−10, 5, +10) | −X |
| 3 | (−10, 5, −10) | −Z |

---

## Crossing detection

For the active gate the planner computes a signed distance from the drone to the gate plane:

```
sideScore = (pos − center) · normal
```

`sideScore < 0` is the approach side; `sideScore > 0` is the exit side. Detection is directional — only an **approach → exit** flip (−1 → +1) counts, so a drone drifting backward through a gate is ignored. A sentinel `windowSide = 0` marks the first tick on a new gate, preventing a false trigger before the side has been sampled.

On a directional crossing the planner checks the in-plane (perpendicular) offset from the center:

| Condition | Outcome |
|-----------|---------|
| Crossed **and** perpendicular offset < half the frame | `STATUS_COMPLETED` — mission advances to the next gate |
| Crossed **and** perpendicular offset ≥ half the frame | `STATUS_RESTART` — the gate was missed; recover and retry |

---

## The carrot rides the centerline, not the center

The obvious carrot — "aim at the gate center, `LOOKAHEAD` metres ahead" — has a fatal flaw. As the drone closes in, the position error collapses to zero **exactly at the gate**, so the controller unloads right when precision matters most. With no aerodynamic drag in this sim, whatever lateral velocity the drone carries then coasts it straight through *off-center*, and it misses.

`planner_w1a` instead places the carrot on the gate's **centerline** — the line through the center along the normal — `LOOKAHEAD` ahead of the drone's projection onto that line:

```
carrot = center + (sideScore + LOOKAHEAD) · normal
```

```
            approach          gate
   drone ───────────────────►[   ]──► normal
              ·····●·············|·····●  ← carrot sits LOOKAHEAD past the
                   └ projection  |        drone's projection — beyond the
                                 |        frame as the drone nears it
```

Two things fall out of this:

- **The forward pull never collapses.** Near the gate the carrot sits *past* the frame, so the drone keeps driving forward through the center instead of decelerating at it.
- **It self-centers.** The vector from the drone to the carrot also carries the off-axis offset, continuously steering the drone back onto the centerline. It flies *through the middle*, aligned with the normal.

> **Knobs in `state.K`:** `LOOKAHEAD = 4 m` (carrot distance), `MAX_YAW_RATE` and `YAW_SLEW_LPF = 0.2` (yaw setpoint slew + smoothing). With no drag, cruise speed ≈ `KP_POS · LOOKAHEAD / KD_POS`, so `LOOKAHEAD` is also a speed knob.

## Miss recovery — PHASE_RESTART

A missed gate is not a hard failure. The planner reports `STATUS_RESTART`, and **mission** takes over with a dedicated `PHASE_RESTART`: it points the target back at the step's **start anchor** (the previous gate, or `HOME` for the first), flies there as a plain waypoint, and re-runs the *same* gate. The fly-back is ordinary proximity navigation, so the shared `planner_wp` block is reused to report arrival (`statusReturn`); once back, mission resumes `NAVIGATE` with a fresh `windowSide`.

```
NAVIGATE ──[miss]──► PHASE_RESTART ──[back at anchor]──► NAVIGATE (retry same gate)
```

This mirrors a racing pilot returning to the last clean checkpoint. Restarts are **counted** — the lifecycle validator tracks them and pass/fail includes a restart budget (below).

---

## Pass / fail

Like L4 and Noise, the `lifecycle.after` hook scores the run live and `afterSim` finalizes a verdict. Window flight adds a fourth criterion to the usual three:

| Check | Pass when |
|-------|-----------|
| Laps | `lapsTotal ≥ REQUIRED_LAPS` |
| Duration | completion tick `≤ MAX_TICKS` |
| Cross-track | accumulated error (IAE) `< ACC_ERR_LIMIT` |
| **Restarts** | `restarts ≤ MAX_RESTARTS` |

`MAX_RESTARTS` defaults to `-1` (not applicable) for waypoint courses, so it is skipped there; window models opt in with a real budget. The infoOverlay shows the live score (e.g. `3/4`) and a final PASS/FAIL.

## Edit the navigator

`navigator_w1` is shared across the whole w1 family — only the planner differs between W1a and W1b. It is a cascaded position → attitude → rate controller that tracks the carrot. Because the yaw loop is a pure-P controller on a noisy heading measurement, it low-passes `attitude.y` (`YAW_MEAS_LPF`) and runs a softer `KP_YAW_OUTER` to stop the drone vibrating its heading left/right while it tracks the carrot.
