# Quad L4 — the reference architecture ⭐

**Quad L4** flies the exact same 4-waypoint rectangle as L3. The flight is unchanged; the point of L4 is the *structure*. This is the model every later one is built on — the recommended starting point if you only read one in depth. Three ideas carry forward into every model after it:

1. **A shared block library** — the flight stack lives in a reusable `lib/quad`, not inside the model.
2. **A static portion of the state bus** — constants are frozen into `state.K` once, kept out of per-tick history.
3. **A lifecycle block** — `beforeSim`/`before`/`after`/`afterSim` hooks own setup, teardown, validation, and the model's own pass/fail test.

```
lifecycle (beforeSim → state.K)
    │  constants + route, frozen once
    ▼
world ──► mission ──► planner_wp ──► navigator_wp ──► fc_acro ──► hw ──► world
                  ▲       │
                  └───────┘
                  stepStatus
    ▲
lifecycle (after → validator + simTest, every tick)
```

---

## The lifecycle block

Earlier models had no concept of *when* code runs relative to the simulation — every block simply executed once per tick. L4 introduces a block with four hooks that fire at distinct points in the run:

| Hook | When it runs | What it does here |
|---|---|---|
| `beforeSim` | once, before the first tick | returns the constants bag + mission route → becomes `state.K` |
| `before` | each tick, before the block loop | reserved (no-op in L4) |
| `after` | each tick, after the block loop | runs the cross-track **validator**, then the **simTest** scorer; stops the run at `simDuration` |
| `afterSim` | once, when the run stops | finalizes the PASS/FAIL verdict |

This is where the **separation of concerns** sharpens. In L3 the validator was its own block competing for a slot in the tick loop. In L4 measurement and scoring are *lifecycle* concerns, not flight-stack concerns, so they live in `after` — the flight blocks (`mission`, planners, `fc_acro`) stay purely about flying, and the lifecycle block owns everything about *running and judging* the simulation.

Because the lifecycle source is editable like any block, the constants, the success criteria, and the validator math are all in one place you can open and change.

## The static portion of the state bus

`beforeSim` returns a bag of constants — gains, limits, frame geometry, the mission route, and the pass/fail thresholds. The engine runs it **once**, freezes the result, and exposes it to every block as `state.K`.

This splits the state bus in two:

- **Dynamic state** — position, attitude, mission phase, validator stats. Changes every tick; recorded into history so the chart scrubber can replay it.
- **Static state (`state.K`)** — constants and route. Computed once, **never written into per-tick history**, and immutable to the blocks that read it.

The payoff is both conceptual and practical. Conceptually, a block declares its dependence on a constant by reading `state.K.MAX_THRUST_N` — the same value `fc_acro`, `hw`, and `navigator_wp` all share, so the "these constants must agree" couplings become a single source of truth. Practically, a 5000-tick run no longer copies the entire constants bag into 5000 history frames.

Editing a value in the lifecycle source and restarting re-runs `beforeSim`, so the whole stack retunes at once.

## Separation of concerns between blocks

The flight stack is partitioned so that each block owns exactly one responsibility, and the *interfaces* between them are the contract:

| Block | Owns | Knows nothing about |
|---|---|---|
| `mission` | phase machine + step cursor | waypoint geometry, completion checks |
| `planner_wp` | completion check only | steering, attitude, motors |
| `navigator_wp` | position → AETR sticks (the cascade) | motor mixing |
| `fc_acro` | AETR sticks → motor rates | waypoints, missions |
| `lifecycle` | constants, validation, pass/fail | how anything flies |

Mission no longer performs the completion check; it reads a single `stepStatus` number the active planner publishes and dispatches on it (`RUNNING → tick`, `COMPLETED → advance`, `FAILED → abort`, `RESTART → retry`). That one-number protocol is what makes new waypoint types (gates, coordinated turns) an *additive* change: drop in a sibling `planner_x + navigator_x` pair that speaks the same status protocol and shares the AETR bus, and mission needs no edits. The racing models do exactly this.

`navigator_wp` normalizes its rate command by `MAX_RATE_*` constants that **must** equal `fc_acro`'s — and now both read the same `state.K` values, so the symmetry is enforced by the shared constant rather than by two copies kept in sync by hand.

## Model testing in the infoOverlay

L4 turns the model into a **self-checking regression test**, surfaced live in the bottom-left overlay. The `after` hook runs `simTest` every tick — a small function that evaluates the success criteria and returns how many pass:

| Criterion | Pass condition | Overlay row |
|---|---|---|
| Laps completed | `lapsTotal ≥ REQUIRED_LAPS` (5) | **Total laps** `x/5` |
| Within tick budget | `tick ≤ MAX_TICKS` (2200) | **Duration** `tick/2200` |
| Tracking accuracy | `accErr < ACC_ERR_LIMIT` | **Acc error** `x/limit` |

The run **early-stops the moment the required laps are done**, so the final tick reflects *how long* the flight took — that is what the duration criterion judges. (A separate `simDuration` hard cap stops a run that never reaches the lap count.)

The accuracy criterion uses **accumulated cross-track error** — the sum of `currentErr` over every NAVIGATE tick (an IAE, *Integral of Absolute Error*). It is not in metres and grows with the length of the flight, so it conflates "flew longer" with "flew worse" — but since the duration check bounds run length separately, it stays a useful tracking-quality figure.

While the run is in progress the **Pass** row shows the live score — `2/3` — in yellow. When the run stops, `afterSim` evaluates the criteria one final time and commits the verdict: the row turns green **`3/3 PASS`** or red **`x/3 FAIL`**.

Because the criteria and their thresholds live in the lifecycle source, this is a tunable acceptance envelope, not a hard-coded one. Open the editor, raise a gain or tighten a limit, restart, and watch whether the run still clears the bar. Every value shown against a limit reads its denominator straight from `state.K`, so the overlay always reflects the current criteria.
