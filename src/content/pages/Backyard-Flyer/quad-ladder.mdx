# Quad Ladder — yaw-aware navigation through a vertical gate stack

**Quad Ladder** simulates a common FPV racing track element: three gates stacked vertically, each entered from the opposite side to the one before. Flying a ladder requires the drone to arc around the structure between gates while simultaneously climbing to the next altitude — and to pre-rotate its yaw heading so it arrives already pointing in the right direction.

Two things are new in this model:

1. **Mixed step sequences.** The mission interleaves positional waypoints (advance on distance) with window gates (advance on crossing), encoding the full approach-arc-cross-arc pattern in a single flat list.
2. **Yaw-aware navigation.** The path planner outputs an explicit yaw setpoint (facing the carrot), and the navigator decomposes roll/pitch commands in the drone's actual body frame rather than always assuming yaw = 0.

```
mission ──► fc_path_planner ──► fc_navigator ──► fc_stabilizer ──► hw ──► world
```

| Block | What changed |
|-------|-------------|
| `mission` | Mixed waypoint/gate step sequence; alternating approach normals per gate |
| `fc_path_planner` | Outputs rate-limited `yawSetpoint`; gate steps use gate normal, waypoint steps use direction to target |
| `fc_navigator` | Yaw-aware: rotates roll/pitch demands into body frame using current yaw |
| All others | Unchanged from W1b |

## The ladder element

In FPV racing a *Jacob's Ladder Switchback* is a vertical stack of gates entered from **alternating sides** — the drone weaves through the structure rather than arcing around the outside each time:

```
                    [Gate 3]   y = 11  ◄── front entrance (from x=5, left)
                        │
         arc left  ─────┘   (exit +x → arc to z=+7, climb y=7→11)
                        │
                    [Gate 2]   y = 7   ──► back entrance (from x=19, right)
                        │
         arc right ─────┘   (exit −x → arc to z=−7, climb y=3→7)
                        │
                    [Gate 1]   y = 3   ◄── front entrance (from x=5, left)
                        │
         fly around left side (origin → x=5, z=+7)
```

The drone starts at the origin facing +X. Gates alternate approach direction — M1 and M3 are entered from the **front** (x < 12, crossing going +x); M2 is entered from the **back** (x > 12, crossing going −x). This weaving pattern avoids wide outside arcs and keeps the drone threading through the structure. "Left" and "right" refer to z > 0 and z < 0 respectively.

## Step sequence

The mission encodes the full maneuver as nine steps — a `[waypoint, main gate, guide gate] × 3` pattern:

| Step | Kind | Position | Notes |
|------|------|----------|-------|
| 0 | waypoint | (5, 3, +7)  | arc left to front-left staging |
| 1 | gate | (12, 3, 0)  | M1: cross going +x (front→back) |
| 2 | gate | (12, 3, +4) | G1: exit guide going −x → arc right + climb |
| 3 | waypoint | (19, 7, −7) | arc right to back-right staging |
| 4 | gate | (12, 7, 0)  | M2: cross going −x (back→front) |
| 5 | gate | (12, 7, −4) | G2: exit guide going +x → arc left + climb |
| 6 | waypoint | (5, 11, +7) | arc left to front-left staging |
| 7 | gate | (12, 11, 0) | M3: cross going +x (front→back) |
| 8 | gate | (12, 11, +4)| G3: exit guide going −x → RTH |

Waypoint steps advance when `dist < threshold` (1.5 m). Gate steps advance on the same directional plane-crossing check used in W1a/W1b. The two kinds share the same state fields and are distinguished by a `stepKind` flag the planner reads.

## Yaw-aware navigation

Previous models always command `yaw_des = 0`, so the drone faces +X regardless of where it is flying. That works when the position PID never needs to fight yaw: roll controls +Z acceleration and pitch controls +X acceleration by assumption.

For the ladder the drone frequently flies in the ±Z direction and rotates its heading between gates. If the body frame is rotated by yaw angle ψ, the wrong mapping — pitch → X, roll → Z — no longer holds.

The correction is a frame rotation. For small tilt angles, the world-frame acceleration demands `(ax_des, az_des)` map to body-frame pitch and roll as:

```
pitch_des = (−cos ψ · ax_des + sin ψ · az_des) / g
roll_des  = ( sin ψ · ax_des + cos ψ · az_des) / g
```

At ψ = 0 this reduces to the standard `pitch_des = −ax/g`, `roll_des = az/g`. At ψ = π/2 (facing +Z) it swaps the axes: pitch now drives Z-acceleration and roll drives X-acceleration — which is correct for a drone pointing sideways.

The derivation: the 2×2 matrix mapping `[θ, φ]` to `[ax, az]/g` under yaw ψ turns out to be its own inverse (determinant = −1), giving the closed-form expressions above directly.

The **yaw setpoint** itself comes from the path planner. For gate steps it is fixed to the gate normal direction; for waypoint steps it tracks the direction to the current target:

```
// gate step:    yaw = atan2(normal.z, normal.x)  — 0 or π for this ladder
// waypoint step: yaw = atan2(target.z − pos.z, target.x − pos.x)
```

Because all staging waypoints sit at z=0 and the ladder runs along X, the waypoint yaw is always near 0 or π — the same values used at the gates. Transitions are clean: the yaw setpoint barely moves between the staging waypoint and the next gate crossing, so the stabilizer has already settled before the drone arrives.
