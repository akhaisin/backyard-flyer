# Quad C2a — first-class target vehicle

**Quad C2a** upgrades the chase scenario to a *physically simulated target*. In the c1 family, the target was a kinematic ghost — a point that moves along a line with no inertia, no flight controller, and no wind. Here the target is a full quadrotor running the same shared block stack as the interceptor: sensor noise, a WP mission, a flight controller, motor dynamics, and physics.

This is the first model in the **c2** algorithm family, which requires intercepting a target that can overshoot corners, fight wind, and behave differently on every run.

---

## The scenario

The target flies a 10 × 10 m square displaced **+10 m on both X and Z** from the c1 path — its circuit sits entirely in positive X/Z, well away from the interceptor's home pad at the origin.

| Corner | Position | Leg |
|--------|----------|-----|
| SE | (15, 5, 5) | East side → NE |
| NE | (15, 5, 15) | North side → NW |
| NW | (5, 5, 15) | West side → SW |
| SW | (5, 5, 5) | South side → SE |

The target homes at (10, 0, 10) — the centre of its square. It takes off, flies the four waypoints, returns home, lands, and immediately restarts.

The interceptor homes at **(-5, 0, -5)** — outside the target's square, clear of the circuit. Its pre-stage point is its own home pad, so after takeoff it is already there: pursuit begins immediately with no detour. A successful intercept (within 1.5 m) sends the interceptor to RTH and simultaneously forces the target to RTH as well — both reset and the next round begins. If the target completes its circuit before being caught, the interceptor restarts for another attempt.

---

## Block architecture

Both vehicles run the full shared lib stack. The interceptor's `planner_c2a` is the only block that reads across the vehicle boundary — it takes `vehicles.target.pos` as its pursuit target.

```
state.vehicles.target
  noise_target → mission_target → planner_wp_target
                                        │ (statusWp)
                                        ↓
                         navigator_target → fc_acro_target → hw_target → world_target
                         (navigator_wp: drives to step.pos, full angular-rate feedback)

state.vehicles.interceptor
  noise_interceptor → mission_interceptor → planner_c2a ←── vehicles.target.pos
                                                 │ (carrot + yawSetpoint)
                                                 ↓
                              navigator_interceptor → fc_acro_interceptor → hw_interceptor → world_interceptor
                              (navigator_c2: outer-P carrot loop, c2 extension point)
```

| Block | Role |
|-------|------|
| `mission_target` | Standard lib mission FSM: arms, takes off, navigates the four WP corners, RTHs, loops |
| `planner_wp_target` | Proximity checker for the target's waypoints — identical to the L4 planner |
| `navigator_target` | `navigator_wp` — drives to `step.pos` with full angular-rate feedback; the same navigator used by every disturbance model in the shared lib |
| `planner_c2a` | **New.** Pre-stage then velocity-lead pursuit: fly to `step.pos` (the interceptor's home pad — already there after takeoff), latch `preGateDone`, then place the carrot `K.LEAD_DIST` m ahead of the target in its current heading; `STATUS_COMPLETED` triggers `forceRTH` on the target; `STATUS_FAILED` when target enters RTH |
| `navigator_interceptor` | `navigator_c2` — dedicated navigator for the c2 chase family; currently shares the same outer-P carrot loop as `navigator_w1`, reserved for future pursuit algorithm development |

## What changes when the target is physical

With a kinematic ghost the target position is exact and noise-free. A simulated target introduces:

- **Inertia**: the target overshoots corners before correcting. Its actual path is a rounded square, not a sharp rectangle.
- **Speed variation**: the target's speed depends on its own PID tuning and the current leg. It slows as it nears a waypoint and accelerates after.
- **Wind coupling**: both vehicles are disturbed by the same wind. A gust that pushes the target also pushes the interceptor, but not identically — each vehicle's mass and current orientation determine how much the wind deflects it.

The interceptor cannot rely on the target appearing at a predictable position at a predictable time. It reads the target's true physics position every tick.

## planner_c2a: pre-stage then velocity-lead pursuit

```
if not navigating:
  carrot = step.pos    yaw = face step.pos    preGateDone = 0

if preGateDone == 0:
  if dist(quad, step.pos) < PREGATE_THRESHOLD (2 m) → latch preGateDone = 1
  else → carrot = step.pos, yaw = face step.pos

if preGateDone == 1:
  if target.mission.phase ≥ RTH (3) → STATUS_FAILED   (target escaped)
  vel   = targetPos − prevTargetPos1          (per-tick velocity estimate)
  speed = |vel|
  scale = K.LEAD_DIST / speed                 (zero if target is stationary)
  carrot = targetPos + vel × scale            (LEAD_DIST m ahead in target's heading)
  yaw   = face carrot
  if dist(quad, target.pos) < threshold (1.5 m) → STATUS_COMPLETED
```

The pre-stage point is the interceptor's own home pad, so `preGateDone` latches immediately after takeoff — there is no detour.

**Velocity-lead (deviated pure pursuit)** places the carrot a fixed distance ahead of the target along its current velocity direction rather than at the target itself. Because the carrot follows the target's actual heading each tick, it adapts naturally to corners on the circuit without any intercept-time solve or model-speed assumption. Compared to direct pursuit (`carrot = targetPos`) the interceptor arrives on the intercept arc earlier instead of always trailing behind.

**`STATUS_COMPLETED` and target restart**: when the interceptor closes within 1.5 m, the planner sets `stepStatus = 1`. On the next tick `mission_target` reads this and receives `forceRTH = 1`, sending the target straight to RTH. Both vehicles reset simultaneously and the next round begins.

`STATUS_FAILED` fires when the target enters `PHASE_RTH` on its own (circuit complete, not intercepted). The interceptor RTHs; the target continues its natural landing sequence and restarts independently.

## Watch it fly

The red quad is the target; the blue quad is the interceptor. Red spheres mark the target's four waypoints (bright = active, dim = pending, dark = done). A guide line shows the vector from the interceptor to its current velocity-lead carrot. A full-screen banner flashes **INTERCEPTED** on a successful close, or **INTERCEPTION FAILED** when the target escapes.

The bottom-left HUD has five toggles:

| Toggle | Default | Effect |
|--------|---------|--------|
| **Intercept** | ON | Interceptor arms and pursues normally. OFF — interceptor stays in ARMING; toggling back ON arms it immediately. |
| **Wind** | OFF | Zeroes the wind block at source — windsock and wind chart go to zero. |
| **Noise** | OFF | Zeroes all sensor noise standard deviations — both vehicles fly on clean readings. |
| **Trail** | OFF | Show/hide the interceptor's position trail. |
| **Guide** | ON | Show/hide the guide line from the interceptor to its current carrot. |

The bottom-right HUD has a **Trail** toggle (OFF by default) for the target's position trail.

## Mission phases

Both vehicles run independent mission FSMs. A successful intercept resets both simultaneously: the interceptor reaches RTH normally; the target receives a `forceRTH` pulse and cuts its circuit short, landing and restarting for the next round. A failed intercept (STATUS_FAILED) sends the interceptor to RTH while the target finishes its natural landing sequence independently.

## Edit the intercept planner

`planner_c2a` implements **velocity-lead pursuit**: it estimates the target's per-tick velocity from the last two positions (`targetPos − prevTargetPos1`) and places the carrot `K.LEAD_DIST` metres ahead in that direction. Try changing `LEAD_DIST` in the `lifecycle` block (under `interceptor:`) to see how the lead distance trades off between cutting ahead of the target and overshooting.
