# Quad W1 Combined — W1a vs W1b side-by-side

Two complete drones fly at once, each a full copy of the shared flight stack, so the **carrot** ([W1a](/Backyard-Flyer/quad-w1a)) and **pre-stage** ([W1b](/Backyard-Flyer/quad-w1b)) planners can be compared under identical conditions.

- **Blue (A)** — `planner_w1a`: centerline carrot only
- **Orange (B)** — `planner_w1b`: centerline carrot + pre-stage leg

Both stacks live in one state tree under `state.vehicles.a` and `state.vehicles.b`, and a single shared `wind` block disturbs both equally — any difference in miss rate is the planner alone.

```
                        ┌─ vehicles.a:  mission ─► planner_w1a ─► navigator_w1 ─► … ─► world
lifecycle ─► state.K ───┤
            wind ───────┴─ vehicles.b:  mission ─► planner_w1b ─► navigator_w1 ─► … ─► world
```

---

## Two offset tracks, one K

The drones race on **separate** rectangles — track A centered at `(−15, 15)`, track B at `(15, −15)` — so they don't overlap in the 3D view. That meant generalizing the shared `mission`: home and the land pad now come from `state.K` (`HOME_X` / `HOME_Z`, default the origin), so each vehicle can take off and return to its own corner.

Both tracks share one frozen `state.K`. The lifecycle publishes both routes (`stepsA`, `stepsB`); each vehicle's `mission` is handed a small **K view** that swaps in its own `steps` + home. The planner, navigator, and physics blocks just read the shared scalars (gains, `LOOKAHEAD`, gust limits) — those are identical for both.

---

## Dual-vehicle validation

The combined `lifecycle.after` hook runs the same cross-track / restart validator as W1a, **once per vehicle**, writing `vehicles.a.validator` and `vehicles.b.validator`. Each vehicle gets its own multi-criteria pass/fail (laps, duration, accumulated error, restart budget), surfaced in its own corner overlay — blue bottom-left, orange bottom-right — with a live `n/4` score and a final PASS/FAIL.
