# Backyard Flyer

Welcome to Backyard Flyer — an educational app for learning quadcopter control fundamentals.

Use the table of contents on the left to navigate between pages.

# Course structure

Each model in this section adds one layer of realism over the previous one. Read them in order to follow the progression from a simple 3D point-mass to a split cascaded flight controller.

---

## [Floater](#Backyard-Flyer/floater)

The first 3D model. A sphere chases waypoints through space using four blocks — `mission → fc → hw → world` — that will recur in every model that follows.

The flight controller is a single PID on position. There is no attitude, no rotation, no motors — just a point-mass accelerated by a force vector. Hardware is a single thruster with spool-up inertia. Physics is a simple Euler integrator.

**What it introduces:** the four-block pipeline, structured state trees, and the idea that the hardware model sits between the controller and the physics.

---

## [Floater PID — PD vs PID side by side](#Backyard-Flyer/floater-pid)

The same architecture as Floater, but two instances run in parallel on mirrored waypoint paths. One uses a PD controller, the other a full PID. Wind is added as a constant force disturbance.

PD reaches a steady-state error it cannot cancel. PID eliminates it — the integral accumulates until it exactly opposes the wind. The side-by-side layout makes the difference impossible to miss.

**What it introduces:** disturbances, the integral term, and why I is necessary when a persistent force must be rejected.

---

## [Quad L1 — full mission sequence](#Backyard-Flyer/quad-l1)

The first real quadrotor. Four motors, full 6DOF rigid-body physics, proper attitude dynamics. The flight controller is a cascaded PID: an outer position loop commands desired roll and pitch angles; an inner attitude loop drives the motors to reach them.

Both loops live in a single `fc` block. The motor mixer inverts the torque equations to allocate thrust across all four motors. A seven-phase `mission` state machine sequences arm → takeoff → navigate → RTH → land → disarm.

**What it introduces:** quadrotor dynamics, cascaded loops, motor mixing, and a complete autonomous mission sequence.

---

## [Quad L2 — navigator + stabilizer](#Backyard-Flyer/quad-l2)

The same mission as L1, but the single `fc` block is split into two: `fc_navigator` (position → desired attitude + thrust) and `fc_stabilizer` (attitude → motor commands). The four signals they exchange — `roll_des`, `pitch_des`, `yaw_des`, `thrust` — are tracked in a dedicated chart.

The two controllers now have separate source editors and independent gain sets. Changing the navigator's position gains does not touch the stabilizer, and vice versa.

**What it introduces:** separation of concerns in a cascaded controller, explicit block interfaces, and independent tunability of the two loops.

---

## [Quad L3 — yaw-aware navigation](#Backyard-Flyer/quad-l3)

The same mission as L2, but the drone now rotates to face the direction it is flying. The navigator derives a yaw setpoint from the direction to the current waypoint and rotates the roll/pitch demands into the drone's body frame so position control stays correct at any heading.

**What it introduces:** yaw-aware navigation, body-frame rotation of position demands, separate yaw gains to keep torque headroom for roll/pitch.

---

## [Quad L4 — the reference architecture ⭐](#Backyard-Flyer/quad-l4)

The same 4-waypoint rectangle as L3, but rebuilt into the structure **every model after it inherits**. If you read one model closely, read this one — the later models add disturbances and gates *on top of* this skeleton rather than reinventing it.

Four things change at once, and they are the reason L4 is the recommended starting point:

- **A shared block library.** The flight stack (`mission`, `planner_wp`, `navigator_wp`, `fc_acro`, `hw`, `world`) no longer lives inside the model — it lives in a reusable `lib/quad` that each model imports. The model file becomes mostly wiring.
- **A static portion of the state bus.** Tunable constants (gains, limits, frame geometry) and the mission route are frozen into `state.K` once before the run, instead of being duplicated into every tick of history. Blocks read `state.K.*`; the values are immutable to them.
- **A lifecycle block.** `beforeSim`/`before`/`after`/`afterSim` hooks own setup and teardown. The cross-track validator moves out of its own block and into the `after` hook, and `afterSim` finalizes a verdict when the run ends.
- **A multi-criteria pass/fail test.** Instead of one sticky flag, the model checks several conditions — laps completed, ran within the tick budget, lap error and average error under their limits — and the **infoOverlay reports the live score (e.g. `3/4`) and a final PASS/FAIL**.

The flight stack keeps the same overall architecture, but the waypoint path is simpler than L3: mission is a pure phase/step sequencer, `planner_wp` only reports step completion, `navigator_wp` flies directly at the active waypoint while yawing toward its horizontal direction, and `fc_acro` remains a rate-only controller driven by an AETR stick bus.

**What it introduces:** the shared block library, the static `state.K` constants slice, the lifecycle block (setup/teardown + validation hooks), multi-criteria pass/fail testing surfaced in the overlay, and mission/planner separation by step type.

---

## [Quad Noise — wind and sensor noise ⭐](#Backyard-Flyer/quad-noise)

Quad Noise now keeps the same canonical architecture as L4 and layers disturbances on top of it. The whole stack is shared: `lifecycle`, `mission`, `planner_wp`, `navigator_wp`, `fc_acro`, `hw`, `world`, plus shared `wind` and `noise` blocks. The controllers still fly the same waypoint mission structure, but now they do it through noisy sensors and under random gusts.

This makes Quad Noise a good second recommended read alongside L4: L4 shows the clean reference architecture, and Quad Noise shows the same architecture under more realistic conditions. The lifecycle block still owns validation and pass/fail scoring, but this model relaxes the accumulated-error threshold to fit the disturbance environment.

**What it introduces:** the L4 shared architecture operating under external disturbances, sensor noise injected ahead of the full flight stack, wind acting through the shared physics block, and the need for integral action when persistent forces must be rejected.

---

## [Quad W1a — window gates and carrot-and-stick navigation](#Backyard-Flyer/quad-w1a)

Point waypoints are replaced with rectangular window gates. The drone must physically fly *through* each 5 × 5 m frame to advance the mission — hovering nearby is not enough. A new shared `planner_w1a` block owns the window logic: through-the-frame crossing detection plus a **pure-pursuit carrot on the gate centerline**. The carrot rides `LOOKAHEAD` metres ahead of the drone's projection onto the gate's approach axis, sitting *past* the frame as the drone nears it — so the forward pull never collapses at the gate (the failure mode of a naive "aim at the center" carrot), and the off-axis term steers the drone through the middle.

Crossing detection is directional (approach → exit only). A missed gate reports `STATUS_RESTART`, and the mission flies the drone back to the previous gate (its start anchor) and retries via a dedicated `PHASE_RESTART` — mirroring a racing pilot restarting from the last clean checkpoint. Restarts are counted and bounded by a pass/fail budget.

**What it introduces:** plane-based crossing detection, the centerline pure-pursuit carrot, mission-owned `PHASE_RESTART` recovery with a restart-budget pass criterion, and the mission/planner split by step type.

---

## [Quad W1b — pre-stage approach](#Backyard-Flyer/quad-w1b)

The same window-gate mission as W1a with one block swapped: `planner_w1b` adds a **pre-stage waypoint** in front of each gate. Before committing to the centerline run, the drone first flies to a point `preStageDist` behind the gate along the inverse normal, so it settles on the approach axis and oblique entries don't carry lateral momentum into the frame. A `preGateDone` latch prevents the target oscillating between the pre-gate and the gate.

**What it introduces:** pre-stage staging as a path-planning primitive layered on the centerline carrot, and the latch pattern that keeps a two-phase approach stable.

---

## [Quad W1 Combined — W1a vs W1b side-by-side](#Backyard-Flyer/quad-w1-combined)


Two complete copies of the shared flight stack fly at once under `state.vehicles.a` / `.b` — W1a (blue, `planner_w1a`) and W1b (orange, `planner_w1b`) — on separate offset tracks, disturbed by one shared wind block. The lifecycle publishes both routes into a single `state.K` and runs the cross-track/restart validator once per vehicle, giving each its own multi-criteria PASS/FAIL. Any difference in laps completed or restart count is attributable to the planner alone.

**What it introduces:** a dual-vehicle A/B comparison built from one shared stack wired twice, per-vehicle pass/fail, and the home-in-`K` generalization that lets the shared mission fly offset tracks.

---

## [Quad C1a — moving-target direct pursuit](#Backyard-Flyer/quad-c1a)

The window-gate scenario is swapped for a **moving target**: instead of a static frame, a kinematic ghost spawns at a corner of the rectangle and slides at constant speed along each 10 m side, looping all four independently of the mission step index. The drone's goal is to close within the intercept threshold before the target finishes its full circuit. One successful intercept sends the drone RTH; if the target completes the rectangle first the mission restarts.

A new `target_c1` block owns the ghost — no physics, just a point that advances `speed × DT` each tick through its own step list. `planner_c1a` reads `target_c1.pos` each tick and sets the carrot directly there (direct pursuit). If the drone gets within `threshold` metres: `STATUS_COMPLETED`. If the target laps: `STATUS_RESTART`.

**What it introduces:** the c1 chase family — a kinematic ghost target with its own independent circuit, direct pursuit as the simplest viable chase strategy, continuous target loop with per-attempt reset, and wind enabled by default to keep the scenario honest.

---

## [Quad C1b — pre-staged intercept chase](#Backyard-Flyer/quad-c1b)

The same scenario as C1a with a **pre-stage leg** inserted before pursuit commits — mirroring the relationship between W1a and W1b. Before switching to direct pursuit, the drone flies to a fixed point `preStageDist` metres along the target's trajectory from its spawn position. Once within `PREGATE_THRESHOLD` of that point the `preGateDone` latch fires and `planner_c1b` hands off to the direct-pursuit logic.

The pre-stage position is derived from static step data (`pos + preStageDist × normalize(dest − pos)`) and is visible in the 3D scene as a cyan indicator dot — the guide line from the drone points to the pre-stage point while staging, then transitions to track the target directly after the latch. When `preStageDist = 0` the block degrades exactly to C1a.

**What it introduces:** pre-staging as a path-planning primitive applied to a moving-target scenario; the guide-to-carrot indicator that switches between the pre-stage point and the target as staging completes; the `preStageDist` step parameter as an independently tunable approach offset.

---

## [Quad C2a — first-class target vehicle](#Backyard-Flyer/quad-c2a)

C2a marks the boundary between the c1 and c2 families: the target is no longer a kinematic ghost but a **fully simulated quadrotor** running the same shared block stack as the interceptor — sensor noise, a WP mission FSM, a flight controller, hardware dynamics, and physics. The target flies a 10 × 10 m square displaced +10 on both X and Z axes, well outside the interceptor's launch pad at the origin. Both vehicles are affected by the same wind; neither behaves identically run to run.

The interceptor uses `planner_c2a`, which mirrors C1b's pre-stage structure: fly to a fixed staging point (`step.pos = (10, 5, 5)`), latch `preGateDone`, then switch to live pursuit of `vehicles.target.pos`. `STATUS_FAILED` fires when the target's mission phase reaches RTH (phase ≥ 3) — meaning the target completed its circuit unintercepted. The target runs `navigator_wp` (same as L4/Noise) for stable position control; the interceptor runs `navigator_c2`, a dedicated navigator reserved for future pursuit algorithm development. Five HUD toggles let you disable the Intercept mission, Wind, Noise, or the trail/guide overlays without editing any source block.

**What it introduces:** the c2 chase family — symmetric dual-vehicle state layout (`state.vehicles.target` / `state.vehicles.interceptor`), shared lib blocks wrapped to vehicle-specific state paths, cross-vehicle state reads in a planner block, and a physically realistic target whose inertia and wind coupling make pure direct pursuit insufficient for reliable intercepts.

## What's next: [Racing](#Racing)

The Racing section takes the same shared block library in a different direction — instead of autonomous position control, it explores open-loop rates control and FPV racing maneuvers.

**[Quad Rates](#Racing/quad-rates)** is the entry point: the route encodes AETR stick values directly (throttle, pitch, yaw, roll) rather than position targets. The drone hovers, flies forward, brakes, spins 180°, returns, and lands — all driven by timed stick commands the way an acro pilot would script a repeatable sequence.
